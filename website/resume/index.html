Note Trace Tool
Many things can go wrong sending the Clinical Notes to the EHR. The initial failures were around UTF-8 and HL7/FHIR character sets.

We knew they were failing, but we didn't know how many. The first part checked DynamoDB tables and scanned Cloud Watch logs for all the failures. This gave us a report that told us

  • how many were failing
  • which characters they had failed for
  • if the characters were in the Title (user can't fix that)
  • if the characters were in the body (the user can fix that and resubmit)
  • how many times the user retried them
  • what changes the user had made between retries
  • if they eventually succeeded or not
That gave us a good idea of the user frustration; I specifically remember 19 retries, but I think the record was over 30. The "Submit" button was definitely flagged in Pendo as one "Users Frequently Rage Click". But it also gave me a list of most offending characters I could pass to development to get them mapped.

Armed with this new tool, L2/L3 support could help assist users in fixing and retrying the ones that were salvageable within 2-3 hours instead of 4-8 days. (A medical note is really only useful if it's ingested within 3-7 days)

Open Telemetry for Novare Desktop UI
New Relic provides easy instrumentation for Mobile. But we needed observability into the Windows and MacOS desktop versions of our application as a requirement before deploying to production. There isn't a native New Relic agent that would handle that, so I used Open Telemetry.

I started by interfacing the New Relic instrumentation, then added an Open Telemetry class. I used pre-processor directives to assign the correct class to the interface at build time.

Then I built a New Relic Dashboard based around the 4 "Golden Metrics" giving up observability and compliance.



General and Special Purpose New Relic Dashboards
  • Desktop Golden Metrics: Built a New Relic dashboard that hooked into the Open Telemetry implementation in the desktop client application, giving teams real-time visibility into 4 key performance indicators
  • Cross-stack Overview: Built a New Relic dashboard unifying frontend UI and backend C# microservice metrics to provide end-to-end visibility
  • Desktop UI Latency Tracking: Immediately upon release to production, we noticed a latency issue in the UI that couldn't be explained with the 4 classic performance indicators. Once I added a page to expose application level errors, the issue was pretty clear. There were several 31-34 second timeouts and a few '503's. This gave me enough information to let the dev teams know which service to check for thread pool exhaustion. Once fixed, the processing times went from ~30s down to under the SLA of 2s.

GCA transcription POC
It's no secret that we used a 3rd party for the transcriptions. We didn't want the front end doing all the work, so we set up a 2-hop design. The front end opens a web socket to the back end and starts streaming audio, the back end opens a web socket to the 3rd party and passes it along. The 3rd party returns the text, and it gets passed all the way back. The system I designed had 4 async tasks, all running concurrently, with buffers to provide decoupling, better testing, and easier trouble shooting. This was unfamiliar territory for me, so I created two stubs, one used Channels, the other one used Pipelines. I tested them for resilience, ease of coding, and used Benchmark Dot Net to gauge performance. This was one of the wildest things I think I've ever done.

Patch Weekend
We were still on private cloud, so once a month, IT Ops would run some scripts to patch in all the security updates to our Windows servers. Sometimes this had surprising and unintended results, so once a month someone (me) would log into every system, in each environment and make sure nothing got broken during the patches. When I first took it over, it was about a two to three hour process starting at 5:00am on a Saturday. I started creating tools and scripts to automate as much of the process as possible. I used Postman for HTTP checks and API responses, Karate to log into portals and dashboards, and I got Jenkins to run it all using Newman. By the time I handed the process over to an off-shore team, it was closer to 30 minutes but you couldn't do real-time testing on Messaging since we don't send out messages before 7:00am. Once we had enough confidence in the system, we tied it to someone's email so if something went wrong, they got a notification instead of sitting watching the scripts run.

Reduced CI/CD from 3 1/2 weeks to fit our 2-week sprints
As we shifted development to 2-week sprints and onboarded several off shore teams, our branching model began causing delays. Development frequently stalled while waiting for releases to finish so the main development branch could open for new work, turning the release cycle into a bottleneck. By implementing a bi-weekly release train, establishing GitFlow-style code freeze dates, and streamlining the testing pipeline, I eliminated those stalls and aligned the entire branching and release process to reliably fit within our new 2-week cadence.

Appointment Reminder Trace tool (Associate SWE)
This was my first project as a new hire, and it was a 'doozy'! When we send out appointment reminders, there are many reasons they may not actually reach the patient, we may not have an email/phone number or a service may have failed. This tool traced the path from where we get the event in GPM all the way to if the reminder was delivered or not.

Before the tool, tracing appointment reminders required a dev assist, or at least a lengthy check by an experienced L3. With the tool, L1/L2 support could easily enter the information from a case to see the result. The tool reduced resolving cases from 3-4 days to 1-2 hours resulting in a much quicker turn around and better customer satisfaction. I really got to know the GPM system well!

GPP Direct Scheduling
My favorite feature, and the one I'm most proud of was Direct Scheduling in GPP! This hooks directly into the EHR so patients can schedule routine appointments on a self-serve basis through the portal.

Allowing patients to schedule their own routine appointments reduces the burden of the scheduling staff and allows them to focus on more complicated issues that actually require their intervention.

One of the challenges we faced was a deep integration with the EHR. We set up daily 'touchpoints' meetings with the EHR teams for closer collaboration. Another one was the complexity of setting up test environments reliably. We documented the procedure and created Golden records for consistent testing before releasing to Production.

I was very excited when it went to EAP (Early Adopter Program), but very few of our early adopters actually tried it out. Once it hit GA, enough of the clients realized the value it added to make it an integral part of GPP. It was one of the coolest things I got to work on up to that point!
